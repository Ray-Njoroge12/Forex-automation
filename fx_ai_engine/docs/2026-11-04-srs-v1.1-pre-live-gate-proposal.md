## 1. What this replaces

SRS v1 section 12 says "No live deployment before successful 30-day demo". ADR 0007 dropped the fixed 30-day demo for development and left the pre-live gate open. This addendum proposes a different gate: no real-account start unless the owner has written a time-limited approval file that the engine checks at start and on every loop. Everything fails closed: a missing, malformed, expired or mismatching input stops the start or halts new entries.

## 2. What the approval file means

The approval file (`fx_ai_engine/config/live_approval.json`, git-ignored; template `fx_ai_engine/config/live_approval.example.json`) is the owner's written, time-limited permission to trade one named account with one named policy. It is read with `FX_LIVE_APPROVAL_FILE` if set. Live start also needs the environment variable `FX_LIVE_CONFIRM` set to `I-ACCEPT-LIVE-RISK-<account_login>`.

| Field | Meaning |
| --- | --- |
| `schema_version` | Integer, must be 1. |
| `approved_by` | Name of the person approving. Written to the audit log. |
| `approved_at_utc` | ISO 8601 time with timezone. |
| `expires_at_utc` | ISO 8601 time with timezone, later than `approved_at_utc`. Live halts at this time. |
| `account_login` | MT5 account number. Must match the bridge and the EA status file. |
| `account_server` | Exact MT5 server name. Must match. |
| `policy_mode` | Must be `micro_live`. |
| `policy_hash` | 64 lowercase hex characters. Must equal the hash of the policy the engine runs. |
| `strategy_id` | Must be `trend_pullback_v1`, the only strategy today. |
| `ea_version_min` | Oldest accepted EA build, `YYYY.MM.DD-N`. |
| `starting_balance_usd` | Balance at approval, in dollars. The loss limit is measured from it. |
| `max_total_loss_usd` | Dollar loss at which the engine stops for the run. |
| `max_orders_per_day` | Integer, at least 1. |
| `max_lot_per_order` | Lots per order, greater than 0. |
| `evidence` | Object `{verdict_path, sha256}`. See section 3. |
| `evidence_waiver` | Object `{reason, accepted_by}`. See section 4. One of the two is required. |

Keys that start with `_` are ignored. Unknown other keys, duplicate keys, wrong types (a boolean where a number is expected), timestamps without a timezone, and uppercase hashes make the file malformed.

## 3. Evidence rule

The `evidence` route points to an authenticity-gate (R2) verdict file. The engine accepts it only if the verdict is `PASS`, `evidence_status` is `EVIDENCE_ELIGIBLE` (the value `research/authenticity_gate.py` writes; `NOT_EVIDENCE` otherwise), the file's sha256 equals the approval's `sha256`, and the verdict's `policy_hash` equals the approval's `policy_hash`.

Limitation today: `backtesting/run_replay.py` hard-codes `core_srs` (line 196) and has no policy-mode option. No PASS verdict can therefore carry the `micro_live` hash, and a waiver is the only route until the backtesting/research owner adds a policy-mode argument.

## 4. Waiver rule

A waiver lets live start without a verdict. It is the owner's decision, with the person accepting the risk named. It is loud: a CRITICAL log line at start and every 4 hours, a persisted CRITICAL `LIVE_EVIDENCE_WAIVER` risk event at the same times (which also raises the risk alert), and the health fields `live_evidence_waiver` and `live_waiver_reason` on every loop. If both `evidence` and a complete `evidence_waiver` are present, the waiver is used. A waiver with an empty field is ignored.

## 5. Caps and loss limit

- `max_total_loss_usd`: when `starting_balance_usd` minus account equity reaches it, the engine halts new entries and stays halted until restart. Equity includes floating result. Deposits and withdrawals are not tracked: **OPEN POINT for the owner.**
- `max_orders_per_day` and `max_lot_per_order`: the EA reports its own limits in `status.json` `live_guard`. The EA values must be equal to or stricter than the approval's, otherwise `LIVE_GUARD_MISMATCH`.
- Values in the example file (3.0 dollars, 4 orders, 0.01 lot) are placeholders. **OPEN POINT for the owner: all three caps.**

## 6. Kill switch

Creating the file `<bridge root>/KILL_SWITCH` stops new entries on the next loop (`LIVE_KILL_SWITCH`). It never closes positions. A file that cannot be checked (any error except "not found") also halts. Removing the file clears the halt.

## 7. Per-loop halts and startup refusals

Per-loop halts set the existing trading-halt flag, write one risk event when a code becomes active, and an INFO `LIVE_HALT_CLEARED` when a non-latched code clears. Codes: `LIVE_APPROVAL_EXPIRED`, `LIVE_APPROVAL_CHANGED` (file bytes differ from start; stays until restart), `LIVE_ACCOUNT_CHANGED`, `LIVE_KILL_SWITCH`, `LIVE_LOSS_LIMIT` (latched for the process), `LIVE_LOSS_STREAK_LATCHED`, `LIVE_GUARD_MISMATCH`, `LIVE_EA_STATUS_UNAVAILABLE`, `LIVE_EQUITY_STALE` (equity older than 60 s, zero or not finite), `LIVE_GATE_INTERNAL_ERROR`.

Startup refusals return exit code 2, record a `LIVE_STARTUP_REFUSED` risk event and write nothing to the bridge folder: `LIVE_POLICY_MODE_MISMATCH`, `LIVE_MOCK_FORBIDDEN`, `LIVE_ACCOUNT_IS_DEMO`, `LIVE_ACCOUNT_UNVERIFIED`, `LIVE_APPROVAL_MISSING`, `LIVE_APPROVAL_MALFORMED`, `LIVE_APPROVAL_EXPIRED`, `LIVE_ACCOUNT_MISMATCH`, `LIVE_POLICY_HASH_MISMATCH`, `LIVE_STRATEGY_MISMATCH`, `LIVE_CONFIRM_TEXT_WRONG`, `LIVE_EVIDENCE_MISSING`, `LIVE_EVIDENCE_FILE_MISSING`, `LIVE_EVIDENCE_HASH_MISMATCH`, `LIVE_EVIDENCE_NOT_PASS`, `LIVE_EVIDENCE_NOT_ELIGIBLE`, `LIVE_EVIDENCE_POLICY_MISMATCH`, `LIVE_EA_STATUS_UNAVAILABLE` (status missing, malformed, older than 30 s, or schema not 1), `LIVE_EA_VERSION_TOO_OLD`, `LIVE_GUARD_MISMATCH`, `LIVE_GATE_INTERNAL_ERROR`.

## 8. Relationship to ADR 0007

ADR 0007 removed the 30-day demo from development. This addendum would replace the SRS section 12 gate with the approval file above. Demo testing continues as ADR 0007 describes. The approval file is not evidence of edge: replay shows the current strategy loses after costs (ADR 0006).

## 9. Weekly loss-streak reset procedure

When the loss streak reaches the policy's `LOSS_HALT_THRESHOLD` (3), the engine latches the halt in the database. The latch survives a later win and a restart. Only an operator clears it, and only after review:

1. Stop the engine (the reset tool refuses while it looks alive: metrics younger than 120 s or a health heartbeat younger than 120 s).
2. Review the closed trades: R7 `research.fill_reconciliation`, R8 `research.drift_monitor`, R9 `research.trade_postmortem`.
3. From `fx_ai_engine/`:
   `python -m validation.reset_loss_streak --account-login <N> --account-server "<server>" --operator "<name>" --reason "<why it is safe to continue>"`
   and type the confirmation text `RESET-LOSS-STREAK-<N>` when prompted (or pass `--confirm-text`).
4. Restart the engine with `--mode live`.

Never reset only to keep trading after an unexplained run of losses. The reset writes a `LIVE_LOSS_STREAK_RESET` risk event with operator and reason.

## 10. Expiry and renewal

Keep `expires_at_utc` short (days). At expiry the engine halts new entries. Renewal is a new approval file written by the owner; the engine then needs a restart, because a changed file halts with `LIVE_APPROVAL_CHANGED`.

## 11. What only the owner may do

Approve this addendum and the SRS v1.1 bump; settle the risk value; set the three caps; accept or refuse a waiver; write and renew the approval file; set `FX_LIVE_CONFIRM`; decide whether to reset the loss-streak latch; approve changes to `config_microcapital.py`.

## 12. What is not verified

The EA `live_guard` fields, `KILL_SWITCH` behaviour and the dollar normalisation of cent-account snapshots are assumed from the EA and Bridge track contracts and tested against fixtures only. They need checking on the real terminal.
