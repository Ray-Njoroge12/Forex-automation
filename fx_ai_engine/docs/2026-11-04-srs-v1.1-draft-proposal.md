## 1. Gate G2 comes first

> **Update 2026-11-04 (ADR 0007).** The owner answered G2-START: there will be no 30-day demo. Development and demo testing alternate in owner-started test waves, one frozen release per wave, and each release is evaluated on its own. The freeze, prereg and evaluate tools below are used per release. The 30-trading-day minimum and the "restart the 30-day clock" rule in §3.7 no longer apply to development. The SRS v1 §12 pre-live gate ("No live deployment before successful 30-day demo") is still open for SRS v1.1 (proposed text: C13, decision A4). The rest of this section is kept as written.

The plan's gate G2 (Phase 2) says a 30-day demo should run only on a configuration that shows positive expectancy after 1.5× costs on walk-forward and holdout. Otherwise Phase 2b (strategy redesign) starts first, because "running a 30-day demo on a strategy with negative replay expectancy would waste a month".

The replay batch another session ran on 2026-11-03 reports negative expectancy for every configuration it has finished (section 2.1). **By G2, a 30-day demo should not start on the current configuration.** Whether to start Phase 6 anyway, for example as an operational run whose result is not read as edge evidence, or to go to Phase 2b first, is the owner's decision (open decision G2-START in section 6). This proposal does not make it.

### 2.3 Sample size reference (computed here, not in the plan)

The standard deviation of R over the 6,406 replay trades is 1.09R. Under a normal approximation:

| Closed trades | Std. error of mean R | P(observed mean ≥ +0.25R) if true mean is 0 | … if true mean is +0.25R | … if true mean is +0.5R |
| --- | --- | --- | --- | --- |
| 25 | 0.218 | 12.6% | 50% | 87.4% |
| 50 | 0.154 | 5.2% | 50% | 94.8% |
| 100 | 0.109 | 1.1% | 50% | 98.9% |
| 150 | 0.089 | 0.3% | 50% | 99.8% |

About 118 trades give 80% power to detect a true +0.25R edge against zero (one-sided, 5%); about 198 with the k = 3 family correction used in the Phase 2b cards (z = 2.39). A point-estimate gate set at the target value passes a strategy whose true expectancy equals that value only half the time, whatever the sample. At the replay's rate (6.4 trades per weekday), 30 trading days would give about 190 trades. The live burn-in has executed 1 trade since 2026-11-03 16:30 UTC, so the live rate may be far lower. On the evaluator's fixture, 30 trades with a mean of +0.30R have a bootstrap 95% CI of −0.20R to +0.80R.

## 3. Options per decision (wave 4 draft)

Section 4 gives the stage F proposed text for each of these; the mapping is in section 6.

### 3.1 Replace the §12.2 "average R" metric (D2)

SRS v1 §12.2 item 3 requires average R ≥ 2.0, and §12.3 item 3 aborts below 1.8. `validate_demo.py` computes these over all trades. With a 2.2R target this needs a win rate near 94% to pass and near 88% to avoid the abort (assessment §4.2 item 1).

- **Plan default for D2 (proposed in plan, not approved):** replace it with expectancy ≥ +0.25R per trade after costs, profit factor ≥ 1.3, and average winner ≥ 1.5R. The starter criteria file uses these values as G1–G3.
- The likely original intent was average R of winners. `validate_demo` already reports it as `avg_r_winners`, and the evaluator exposes it as `avg_r_winners_srs`.
- Definitions the tooling uses (from `backtesting.replay_report.trade_metrics`, shared with replay reports): expectancy is the mean R of closed trades; profit factor is gross profit / gross loss in account currency (`profit_loss`), not in R, so the loss throttle affects it; average winner counts trades with R ≥ +0.1R, so break-evens are excluded. The owner may prefer an R-based profit factor; that is part of D2.
- Replay reference: baseline average winner 1.08R and profit factor 0.47. All three proposed gates fail on the current replay.

### 3.2 Replace the §12.3 average-R abort line (O5)

The plan proposes no replacement for "Avg R < 1.8". The starter file keeps a placeholder `A3_AVG_R_REPLACEMENT` with no value (status `OPEN_OWNER_DECISION`). The evaluator reports it as OPEN and does not evaluate it, and `prereg` will not accept an APPROVED file that still has it open. Possible options: expectancy CI upper bound < 0 after N trades; expectancy < 0 after N trades; or no performance abort, leaving only the drawdown and risk-failure aborts. Stage F proposes the first (C18).

### 3.3 Risk per trade during the demo vs the drawdown gates (D3)

SRS v1 sets 3.2% per trade, a 15% acceptance drawdown (§12.2) and a 20% abort and hard halt (§12.3, hard-risk engine).

- **Plan default for D3 (proposed in plan, not approved):** keep 3.2% only if Phase 2 shows the drawdown gate is reachable; otherwise lower it to 1.0–1.5% through SRS v1.1.
- Evidence (section 2.2): on today's replay trades, P(max DD > 15%) over 100 trades is 0.92 at 3.2%, 0.17 at 1.5% and 0.01 at 1.0% (i.i.d.). Over 30 trades it is 0.11, 0.002 and 0.000. Plan Phase 3 item 2 asks that the chosen level's breach probability be stated and accepted. The numbers should be rerun on the configuration that passes G2, if one does.
- A change to risk per trade changes the policy hash. The EA pin and freeze manifest must then be redone (section 3.7).

### 3.4 Minimum trade count (O1)

SRS v1 §12.2 item 1 requires ≥ 25 trades. Plan Phase 3 item 3 says to raise the minimum, or to label 25 trades as an operational check only, because 25 trades cannot tell a 35% win rate from a 45% one (assessment §4.2 item 3). The plan gives no number. The starter criteria file keeps 25 with that note, plus the plan's 30-trading-day minimum (Phase 6). Section 2.3 gives about 118 trades as one reference point. The evaluator returns INCONCLUSIVE below whatever minimum is pre-registered.

### 3.5 "Max 2 trades" vs the 5% combined exposure cap (O4)

Two positions at 3.2% need 6.4%, above the 5% cap. A second trade passes only when volatility scaling cuts its risk to 1.8% or less (assessment §4.2 item 4). Evidence: the baseline replay has 9,592 `PM_EXPOSURE_LIMIT` rejections against 20 `PM_MAX_TRADES_REACHED`. The live burn-in (read-only DB, 2026-11-03) has one open GBPUSD trade at 3.2%, with 10 `PM_EXPOSURE_LIMIT` and 1 `RESERVATION_MAX_EXPOSURE` rejections. The plan (Phase 3 item 4) asks for this to be resolved but recommends no option. Options:
- (a) keep both limits and document that a second trade is conditional on volatility scaling;
- (b) set max open trades to 1;
- (c) lower risk per trade so that two fit under 5% (≤ 2.5%; the D3 default of 1.0–1.5% fits);
- (d) raise the exposure cap, which raises total risk.

This interacts with D3. Stage F proposes (c) through C7 and C8.

### 3.6 Win-rate gates and how gates are applied (O2, O3)

- O2: SRS v1 also requires win rate ≥ 45% (§12.2) and aborts below 40% (§12.3). Plan D2 does not replace these, so the starter file keeps them as `SRS_V1_UNCHANGED`. The replay win rate is 29.6% (37.0% counting R > 0). With expectancy-based gates, a win-rate gate can reject a positive-expectancy configuration or duplicate the expectancy gate. On the evaluator fixture, 13 wins in 30 trades at +2R give +0.30R expectancy and pass G1–G3, but fail the 45% win-rate gate (NO_GO). Keep, lower, or drop: owner's choice.
- O3: gate on the point estimate (as the starter file does) or on a confidence bound (for example, expectancy CI lower bound > 0, metric `expectancy_r_ci95_low`). Section 2.3 shows the trade-off.

### 3.7 Freeze and pre-registration (plan Phase 3 item 6, Phase 6)

These are protocol steps, not new limits:
1. Before the start, freeze the configuration with `research.forward_test.freeze create`. This records the policy hash, the config hash, the EA source and its pinned hash, the compiled EA hash, the protected-path hashes and the git commit.
2. Write the criteria file, have the owner set `status` to `APPROVED` with `approved_by`, put the manifest's `manifest_sha256` in `freeze_manifest_sha256`, then seal it with `prereg seal` while the start is still in the future. Commit both files before the start.
3. Run `freeze check` daily, and pass the manifest to every evaluation. A mismatch makes the run INVALID. Under the no-change rule, a behaviour-changing fix ends the release (ADR 0007; C14).
4. Evaluate with `research.forward_test.evaluate` against the sealed file. The evaluator refuses if the file changed after it was sealed.
5. The plan's Phase 6 abort conditions that the database cannot show (orders outside the EA, hard-risk failures, spread/slippage control failures, live costs against the replay's 1.5× assumption) are listed in the criteria file as manual checks M1–M7 for owner sign-off.

## 5. Notes on specific changes

**C7 risk per trade.** ADR 0001 D3 keeps 3.2% only if Phase 2 shows the drawdown gate is reachable. It is not: with the SRS halts on, the replay hits the 20% hard halt within 7 days of the first trade (2022-12-27 to 2023-01-03), and the R5 sweep gives a 0.90 to 0.92 chance of a drawdown above 15% within 100 trades at 3.2%. The proposed range is the D3 default. The numbers in §2.2 come from a losing strategy; the value is fixed by rerunning R5 on the frozen Phase 2b strategy. A change to `BASE_RISK_PCT` changes the `core_srs` policy hash, so the EA pin and the release freeze manifest are redone in the same change (section 7).

**C8 exposure.** No limit changes. Lowering risk to 1.0 to 1.5% removes the conflict, because two full-size trades fit under the 5% cap.

**C12 and STATUS known issue 33.** Two existing gates can reject routes today: `ML_RANKER_LOW_PROB` when a ranker model file exists (absent now), and the strict canary when `FX_META_LABELER_CANARY_ENABLED` and mode `strict` are set (off by default). Both only reject, but under C12 they are promoted behaviour and run after the Hard Risk Engine. Proposed: keep both disabled by policy (no model file, canary off) until a component passes the C12 promotion rule. The owner may instead ask for them to be made log-only; that is a code change for a later wave.

**C13 pre-live gate.** ADR 0007 removed the 30-day demo from development but left the real-money gate open. The proposed text is one option; real money stays a separate owner decision in any case.

**C15 and C16 thresholds.** A gate set at the target value (+0.25R) passes a strategy whose true expectancy equals that value about half the time, whatever the sample. The proposal gates on the point estimate, as D2 states, and requires the C15 minimum so the estimate has a standard error near 0.10R. Gating on a confidence bound (O3) is the stricter alternative; it is not proposed.
