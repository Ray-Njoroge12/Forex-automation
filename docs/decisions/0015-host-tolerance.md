# ADR 0015: Host tolerance on the Mac (host guard, missed cycles, outage alert, EA ATR cache, gate H1)

Date: 2026-11-05. Status: accepted for development; the EA change (protected path) needs a review by a different model and owner approval before merge.

## Context

The owner's 8 GB MacBook sleeps, runs on battery, throttles MT5 (App Nap) and runs replays next to the engine (`fx_ai_engine/docs/2026-11-04-mac-host-operating-model.md`, STATUS issues 20 and 21). Section 6 of that doc lists five backlog items; section 7 defines gate H1.

## Decisions

1. **One rule set.** `core/host_rules.py` holds the parsers, budgets and rule functions. `validation/host_check.py` (CLI, unchanged output) and the engine use it. The engine evaluates only `guard_checks`: power, sleep prevention, App Nap, replay/research processes, bridge snapshot age (30 s) and swap. It runs about nine short commands and never samples MT5 CPU or calls `footprint`. A probe command that fails to run, times out, exits with 2 or more, or is killed by a signal (negative return code, review finding HT-008) raises `ProbeError`. Process probes (`pgrep`) never read that as "no process": the replay rule BLOCKs in trading mode and MT5 counts as not running (review finding HT-003).
2. **Host guard is an entry block, not a risk limit.** `application/host_tolerance.HostGuard` runs at engine start, every 300 s, every 30 s while blocked, and at the first poll inside each UTC day's trading window. A BLOCK on one of the five rules (or a probe error, fail-closed) stops the decision cycle before any strategy stage: funnel stage `HOST`, reason `HOST_GUARD_BLOCK` per symbol, and risk event `HOST_GUARD_BLOCK` (BLOCK) on entry into the blocked state or when the failing set changes. `HOST_GUARD_RECOVERED` (INFO) is recorded when it passes again. Both are persisted without the Telegram risk alert that other BLOCK events send; the outage alert (decision 6) is the one notification for a stale bridge (review finding HT-002). Feedback, exits, closure recovery and account updates still run every loop. Router housekeeping (stale-signal quarantine) still runs before the check. Locked constants, the Hard Risk Engine and its position at the end of the flow are unchanged. Swap is recorded but never blocks.
3. **Where the guard applies.** Only `--mode demo|live`, not mock, and only on macOS (`sys.platform == "darwin"`); elsewhere it is disabled and says why in the log. Tests get a disabled guard from `tests/conftest.py` and inject their own probes.
4. **Daily host record for H1.** The first evaluation inside the window each UTC day runs `core.host_rules.window_start_checks`: the guard rules plus every other rule that can BLOCK in `host_check` trading mode (memory, disk, MT5 running, connection drops; swap at 4 GB). The WARN-only rules (footprints, MT5 CPU, Max bars, news) are left out. It is persisted as `HOST_GUARD_DAILY_CHECK` (INFO) with `status=` (BLOCK if any evaluated rule blocks), `scope=host_check`, `failed=`, `swap_used_mb=` and every check's status. Entries still block only on the guard rules, so a memory BLOCK at the window start is recorded but does not stop trading (review finding HT-001).
5. **Missed cycles.** Expected cycles are the weekday M15 slots whose start is inside a session (`core/filters/session_filter.py`). Evaluated cycles are slots with a `SESSION`/`PASS` funnel row. Only `execution_mode='mt5'` rows count (`validation/cycle_counter.py`; reported by `burnin_status`). Holidays are not modelled.
6. **Outage alert.** `OutageMonitor` sends one message through `core.alerts` when the account snapshot or the bar exports are stale for more than 120 s inside trading hours, and one when they recover. The bar-export feed is the older of the `status.json` heartbeat and the six `bars_<symbol>_M15.json` files themselves: a file whose last bar is more than one bar behind the clock is stale, and a missing or unreadable file counts as missing. `status.json`'s `latest_closed_bars` is not used, because the EA fills it from `iTime` even when a bar export failed (review finding HT-005). Each file is parsed only when its mtime or size changes. It does nothing when `core.alerts.alerts_configured()` is false and is off in mock mode. A failed delivery is logged and not retried. The episode state (`active`, stale feeds, times) is a JSON file, `fx_ai_engine/database/outage_alert_state.json` (git-ignored), written atomically under an exclusive `flock`. The engine and the watchdog both poll it, so a restart during an outage sends no second outage message, and a recovery that happened while the engine was down is reported once on restart. The watchdog polls every 30 s. It covers outages the engine cannot report: the engine was not running, or a demo start is refused because no fresh account snapshot exists. If the file cannot be written, each process keeps the state in memory (review finding HT-002). Two further rules keep an outage at two messages (review finding HT-006):
   - Engine risk events that describe the same stale file (`STATE_RECONCILIATION_FAILED`, `STATE_STALE` and `LIVE_EQUITY_STALE` for the account snapshot, `LIVE_EA_STATUS_UNAVAILABLE` for `status.json`) are still persisted, but `Engine._insert_risk_event` drops their Telegram alert when the file is missing or older than 30 s and the outage alert covers it. It covers the file when an episode is active, or during trading hours, where a stale feed that lasts past 2 minutes is reported. A feed that recovers within 2 minutes in trading hours therefore sends nothing. Outside trading hours, with no open episode, these alerts are sent as before. Every other BLOCK or CRITICAL event still alerts. `core/live_gate.py` is not changed: its events go through the engine method.
   - The "FX AI Engine Started" message is folded into the episode. An OUTAGE sets a flag in the state file. A start while an episode is active sends no message. The first start after a recovery sends none and clears the flag. A running engine that sees the recovery clears the flag, because it ran through the outage. After that, starts announce themselves again.
   - Boundary: an episode that starts in the last 2 minutes of a session may send neither the outage message nor the folded risk alerts; the next out-of-hours `STATE_STALE` alert still fires.
9. **Guard state across processes (review finding HT-004).** In demo mode, a snapshot older than 30 s fails the demo-account check. A start is then refused before an `Engine` exists. A running engine keeps looping with new entries blocked (decision cycle skipped, `_fail_closed_bridge_uncertainty` re-applied after each account update) and still processes feedback, exits, closure recovery, the guard and the outage alert (review finding HT-007); only a confirmed live account stops it. Both paths evaluate the host guard first (forced, once per unverified episode) and persist `HOST_GUARD_BLOCK`. A refused start uses the evidence context the engine would have used (the run's policy, login and server from `status.json`). The guard's blocked state (`blocked`, failed rules, details) is stored in `engine_runtime_state` under `host_guard_state` on each BLOCK and recovery. A new `Engine` restores it, so its first poll records `HOST_GUARD_RECOVERED` when the host passes, and the same failures after a restart record no second BLOCK. The demo-account rule itself is unchanged: entries stay refused until a fresh demo snapshot is verified. A start that fails earlier, because `status.json` is stale and the bridge cannot connect, has no account to record against and records no guard event; the outage alert still reports it.
7. **EA ATR cache (protected).** `GetATR` reuses one `iATR` handle per symbol/timeframe/period (cache of 16, reset if full) and `OnDeinit` releases them. Order placement and the envelope checks are unchanged. EA build `2026.11.05-1`. A side effect: MT5 calculates a new indicator handle asynchronously, so the old code could read a handle before it had calculated. In that case `GetATR` returned 0 and the trail skipped that tick. A cached handle has calculated by the next tick, so the trail may now move on ticks where it used to skip. The trail rules are the same.
8. **Gate H1 evaluator.** `python -m validation.gate_h1` (read-only) checks, per completed trading day: the daily host record within 15 minutes of the window opening with `scope=host_check` and PASS (any other scope is NO_DATA), swap below 1500 MB in it, at most 6 MT5 connection drops in the window (terminal logs, local time), no Sleep/DarkWake in `pmset -g log` during the window, and zero missed cycles. Missing data is NO_DATA and does not pass. H1 passes on 5 or more consecutive completed trading days, counted back from the latest.

## Consequences

- A host problem during trading hours now appears as a reason code, a missed-cycle number and (with Telegram configured) two messages. Before, it showed only as silence.
- H1 cannot be met until the engine runs in Mode T with this build, because the daily host record is new.
- Not measured from recorded data: the WARN-only MT5 settings (Max bars, news, footprint, CPU) and the physical setup (UPS, backup link).
